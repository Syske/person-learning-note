去年 2 月我在这个号上写过一篇《AI 时代的认知保卫战》，聊依赖 AI 这件事。

有读者留言问我：那你打算怎么办？

我当时没答上来。真的没答上来，不是谦虚。

那篇文章我写得挺顺的，苏格拉底、波兹曼、阿伦特都用上了，结论也很正确——过度依赖会让人变懒、丧失探索欲。发完我自己还挺得意。

但有个问题我当时没意识到：**那篇文章里除了发牢骚，没有任何一句能指导我明天怎么做。**

大半年之后我给自己写了个东西，现在它有 33 个模块、20 条工作流、19 份治理文档、9 份架构决策记录。637 次提交。

它是 Python 写的，而我是个 Java 后端。

已经开源了，Star 数是 2。

* * *

## 九月那件事

2026 年 9 月 24 日，我执行了一次提交。

提交信息里我用反引号包了个示例，写的是 `git clean -fdx`。命令是 `git commit -m "..."`，双引号包起来的。

双引号里的反引号，shell 当成命令替换。

然后它就真去执行了。

`-f` 免询问，`-d` 连目录，`-x` 连 gitignore 掉的也一起删。工作树里那些没被跟踪的东西，一瞬间没了。

200 份运行日志，指标快照，本地环境配置。没了。

git 里版本化的文件没事，100 多次提交都在。但那些日志我当初就是设计成"机器本地、不入库"的，理由听着很合理对吧——日志又不是代码，没必要进仓库。

现在我知道那个理由有多天真：**不入库不等于有备份，它只是等于"可以被一条命令清掉"。**

后来我写事故报告，作者那栏填的是 "AI Maintainer（事故责任方：本会话）"。

不是甩锅给 AI。是我在用 AI，是我设计的系统允许了这件事。

* * *

## 有点后怕的地方

如果是我自己手敲错了命令，那没什么好说的，就是我蠢，我认。

但这次不是。

这次是 AI 生成了一条命令，然后它把命令执行了。

我自己敲错，代价是一句话打错了。AI 敲错，它是真的跑。而且跑得干净利落，毫无保留。

**它没报错，没犹豫，也没反问一句"你确定要删？"**

它就干了。

这才是我觉得真正危险的地方。AI 犯错和人犯错不一样——**人错的时候你看得出来，它错的时候你看不出来，因为它看起来完全正常。**

去年我在那篇文章里写，AI 生成的方案"缺乏技术选型的论证过程"。当时觉得这是个惋惜。

现在我改个说法：论证过程里有一部分东西是"出错之后谁买单"。

那 200 份日志没了，对它来说是零成本，对我是两周的排查记录。

* * *

## 于是我开始给它立规矩

出事之后我做的事挺笨的。

我开始给 AI 写规矩。

不是文档里写"请注意代码质量"那种，是能卡住它的。

比如现在这些是硬规则：

**破坏性命令默认拒绝。** `git clean -fdx`、`git reset --hard`、`rm -rf` 全部默认不执行。非要执行先跑 `--dry-run` 把清单列出来，等我确认。这条就是那件事的直接产物。

**提交信息不许用 `-m` 带反引号。** 一律 `git commit -F -` 配 `<<'MSGEOF'`。

还有一条是老毛病了：我有个 skill 写到 1400 行，然后 AI 开始复读——在回答里把文件里已经写过的段落重复一遍，两遍，越写越啰嗦。文件太长它抓不住重点，就开始"回忆"。现在超过 1000 行就报警。

再比如每个 skill 必须有合法的 YAML frontmatter。这条我最后加的。因为 description 缺失的 skill，AI 根本不知道什么时候该调它，就在那儿安静地躺着一个部门都没有。

description 不是描述，是契约。

现在这样的文档有 19 份。

它们不是设计出来的。

* * *

## 一个写 Java 的，怎么搞出个 Python 东西

可能有人会问。

其实挺顺的。

Java 后端日常就是 Maven。多模块、`-pl` 选范围、`mvnw`、Surefire 那套失败模式。这些东西我踩了快十年了。

第一次让 AI 帮我跑 Maven，我就发现不对：

`bugfix` 那个 skill 里 `mvn -pl ... test` 散在 3 个文件；
`implement` 的 validation.md 里有一份 `mvn -pl ... compile`；
`mock-test` 的 diagnosis.md 里还有一份 `mvn test -Dtest=...`。

三套写法。范围选择不一致，wrapper 处理不一致，失败诊断也不一致。

后来我开了个 ADR，编号 0003，标题就叫 java-maven as Foundation Skill。里面有一栏 Consequences，分正反两面。正面是统一之后的好处，反面写了两条：skill 都得等它跑完，它可能变成瓶颈。

我为啥要写负面？因为那确实是我自己选的。

技术号里最不缺的就是"这个方案很好"，最缺的是"这方案让我付出了什么"。

## 五层和七步

系统的结构长这样：

| 层 | 管什么 | 一句话 |
|---|---|---|
| Workflows | 决定做什么 | 只编排，不实现 |
| Runtimes | 执行怎么做 | 模板化，不即兴 |
| Governance | 约束行为 | 19 份规矩，违反即卡 |
| Standards | 定义质量 | BLOCKER / ERROR 分级 |
| Skills | 提供方法 | 33 个 |

主链七步：

```
prepare → spec → dev-setup → develop → review → verify → release
bugfix 是并行分支
review 打回 → 回 develop
verify FAIL → 回 develop
```

那两个"回 develop"是我最看重的。**AI 写的代码不是终点，是草案。**

我算过，一个需求从开始到进 release 平均 3.4 轮往返。慢，真慢，比我自己闷头写慢。

但慢在不确定性上，不是慢在打字上。这个区别我觉得挺重要，虽然不一定所有人认同。

* * *

## 说个让人有点难堪的事

写这套东西的时候，我也在用 AI。

13 个 CLI 命令的骨架是 AI 生成的，快、可运行、能跑。这部分我不打算假装是自己敲的。

但有一件事它反复搞错。

menu.yaml 的边界该怎么切，i18n 的文案该怎么拆——错了四五次，每次错法还都不一样。

后来我想明白了：**那是我们组的约定，不是通用知识。**

AI 知道"多语言项目应该做国际化"。它不知道在这套系统里结构和文案为什么非得拆成两个目录，因为这个决定是我们踩完坑才定下来的。

所以我得先把规则写出来它才能做对。

而"把规则写出来"这个动作本身，就是这 19 份文档的来路。

7 月 31 号第一次提交，到今天 74 天，637 次。其中 172 次是文档，128 次是功能，104 次是修复。

文档比功能多。

这不是软件项目正常的比例。

这一年真正的收获也不是这个系统，是我终于搞清楚自己组的约定到底是什么。

去年写"要防止变成只会用 AI 的工程师"，那句话当时是没有落点的。

现在有了。先得知道自己在守什么，才谈得上守。

* * *

## 那张架构图

去年那篇文章末尾我写过一段，说我在架构图上标注两种路径，蓝箭头是 AI 建议，红线是人的决策轨迹。当时就当成个比喻写的。

现在它变成机制了。

蓝箭头画起来特别快，一条两分钟，线条顺、走向漂亮，每一段看着都合理。

红线慢，得停下来想：这个能不能动，影响谁，违反我们组哪条规矩，想清楚才落笔。

很多个下午我画着画着会笑出来。

因为发现去年担心的那件事压根没落到别人身上，它落我身上了。

这里有个我没解决的悖论：

**我造这东西是为了防止自己变依赖，但造它的过程就是我一点点把判断交出去的过程。**

我没解开，只是让它看得见了。看得见的代价比看不见好一点，大概。

* * *

## 最后

去年我在文末改了句《浮士德》：

> 停一停吧，你这美妙的算法！我愿用百行低效代码，换取一次真实的认知战栗。

今年想往下接一句。

想明白之后我觉得，"停一停"不是为了反对什么。它的对立面不是 AI，是"不用动脑"。

停一停是为了画那条红线。笨，慢，不好看。但是你的。

那次事故之后我还改了个想法。本来以为立规矩是为了管住 AI，写完发现不是。

**规矩的真实作用是让我自己变得可控。**

这系统现在 Star 2，Fork 0。离好用还差得远，主要就我自己在用，规模化的验证没做过。我也不太想拿它讲什么方法论，更不劝谁装。

但如果你也在用 AI 写代码，如果你也有过那种"跑通了、可我就是不敢 merge"的二十秒——

欢迎来看看。顺便翻翻那份事故报告。

`github.com/Syske/ai-system`

回复【**aic**】，19 份治理文档清单、7 步工作流的契约文件、还有那份事故报告，都发你。

要是你身边也有人正在拿 AI 赶进度，转给他看看。

让他知道还有一种用法，慢一点，但站得住。
