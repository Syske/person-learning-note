去年 2 月我在这个号上写过一篇《AI 时代的认知保卫战》，讲依赖 AI 这件事。

那篇文章我写得挺顺的，苏格拉底、波兹曼、阿伦特都用上了，结论也很正确——过度依赖会让人变懒、丧失探索欲、变成 AI 的附庸。

发完还挺得意。

后来有读者留言问我：那你打算怎么办？

我当时没答上来。说实话不是谦虚，是真没答案。那篇文章里除了发牢骚，没有一句能告诉我明天该干什么。

大半年之后我有了答案。先说结论：

**我没上岸。我下水了。**

然后我发现，去年那篇文章有点白写——不是内容错了，是姿态错了。

* * *

## 一、被安排的那次迭代

今年 6 月，TL 找我聊了一次。原话大概是这样：

> 公司最近一直在推动 AI 提效，后续会全面推开 AI Coding，
> 我们要抓住这个所剩不多的时间窗口，积累 AI Coding 的经验。

“所剩不多的时间窗口”——这词我记住了。

它不是“上面要求你用”，是“再不学就晚了”。这两句话的意思完全不一样，前者是交差，后者是船票。

我 Java 后端做了快十年，AI 这块停留在“写写脚本、问问问题”这个水平大概两年了。突然被推到这条路上，说不慌是假的。

但那会儿没得选，硬着头皮开始试。一边查资料一边试。

**最开始只有一个 skill。**

那东西还有点用，我用它完成了需求的前期设计和方案评审。这段确实跑通了——**如果你只是想让 AI 帮你"想清楚要做什么"，一个 skill 就够了。**

## 二、然后就撞墙了

进了开发阶段，麻烦来了。

我发现光靠人工会话 + 提示词，效果真的不行。写出来的代码能看懂，但不好用。

于是我把工具链往上拉：Claude Code、Superpowers、OpenSpec，能上的都上了。

结果还是不行。而且不是"效果一般"这种不行，是**越用越糟**的那种不行。

具体说就是三件事：

**第一，输入得反复重来。** 同样的背景、约定、分层规范，每次开新会话都得重讲一遍。我不是在跟 AI 协作，我是在反复给它做入职培训。

**第二，输出得反复要求修改。** 改一版，它理解偏了；再改，又偏到另一个地方去。我开始怀疑是我表达有问题。

**第三，也是最气人的——它改的东西不对。**

不该改的它动了，改了也就算了，它顺手还给你改坏。
该改的它没改到位，或者改得乱七八糟。

最难受的就是这个：**你花了时间 review 它，结果发现它干的活儿既没解决问题，还引入了新问题。**

那段时间我挺怀疑人生的。工具都拉满了，人也不是不会用，怎么就是不对。

也是那时候我开始认真跟 ChatGPT 聊这件事——不是问代码怎么写，是问**方向**。

## 三、7 月 22 号，有人把话说破了

我找到了最早的一条记录，7 月 22 号 13:05。

我问的是：

> 结合我们之前聊的，关于 pi agent 的 vibe coding 最佳实践，你有什么建议

它的回答里有这么一段：

> 结合我们这几个月的聊天，我发现你其实已经不是在研究 AI Coding Tool 了，
> 而是在构建一套自己的 AI Coding System。
>
> 你的路线实际上已经比较清晰：
> OpenSpec（需求） → Runtime（执行） → Skill（知识） → Project（业务） → Pi Agent（执行器）
>
> Pi 在这里并不是主角，它只是 Agent Runtime，真正决定效果的是 Context Engineering。

我当时看到这段的感觉挺复杂的。

一方面，它说的确实是我在干的事——我自己都没总结出来，它给总结完了。

另一方面，它还有点扎心：**它说得对，说明我确实已经走偏了。**

我以为自己是在学怎么用 Pi，其实我早就在造自己的东西了。

而且最后那句话我现在还常常拿出来说：**Pi 不是主角。**

我后来做的所有判断，基本都是从这句推出来的——Agent 只是个执行器，真正决定效果的是你给它塞了什么上下文。

从那天起，skill 开始往系统的方向长。

## 四、一个 skill 是怎么长成系统的

过程没什么玄学，就是一层一层被逼出来的。

我翻了下这四个月的 token 消耗：

| 月份 | token | 环比 |
|---|---|---|
| 6 月 | 8.87 亿 | — |
| 7 月 | 23.17 亿 | +161% |
| 8 月 | 31.96 亿 | +38% |
| 9 月 | 0.54 亿 | **−98.3%** |

四个月合计 64.55 亿。

先说清楚一件事，免得被误会：**9 月还有个别客观因素——DS 那边涨价了，我切到了别的平台。**

所以这 98% 不能全算在系统头上，**这里头有一部分是省下来的钱，不是我省下来的活。**

那剩下的是什么？

6 到 8 月那 64 个亿，是在**试错**。反复讲、反复改、反复推翻重来，全是重复劳动。
9 月降到 0.54 亿，是因为那些该重复的部分终于被固化下来了——

该说的话进了文档，不该动的地方设了红线，该走的步骤排进了工作流。
**它不再需要每次都从零跟我确认一遍。**

换句话说，这套系统的产出不是"我更会写 prompt 了"。

是**大量原本要重复解释、重复检查的活儿，被一次性固化掉了。**

这个数字我只当参考，不当成结论——毕竟中间换了平台。
但方向我能确认：**同样的活儿，现在比半年前少啰嗦多了。**

* * *

中间有几个节点我印象很深。

一个是**发现我花在重复解释上的时间比写代码还长**。同一个分层约定，这周说一遍，下周再说一遍，第三周它还犯。那次我意识到，靠我的嘴实时喂是喂不过来的，必须落成文件。

再一个是**意识到 AI 犯错的地方，通常是我没说清楚的地方**。它不是笨，它是在按它理解的世界做事。那既然这样，世界的定义就该由我给。

最后一个最关键，是**搞清楚"我们组的约定到底是什么"**。

这个有点反直觉。我一直以为写文档是在整理 AI 的用法，写着写着才发现，我其实是在整理我自己团队的规矩——哪些必须遵守，哪些绝对不能碰，哪些要走流程。这些东西一直在，只是没人写下来过，我也没认真想过。

**AI 不知道我们组的规矩。这不是它笨，是没人告诉过它。**

现在它有 33 个模块、20 条工作流、19 份治理文档、9 份架构决策记录。

637 次提交。

结构大概是这样：

| 层 | 管什么 | 一句话 |
|---|---|---|
| Workflows | 决定做什么 | 只编排，不实现 |
| Runtimes | 执行怎么做 | 模板化，不即兴 |
| Governance | 约束行为 | 19 份规矩，违反即卡 |
| Standards | 定义质量 | BLOCKER / ERROR 分级 |
| Skills | 提供方法 | 33 个 |

主链七步：

```
prepare → spec → dev-setup → develop → review → verify → release
bugfix 是并行分支
review 打回 → 回 develop
verify FAIL → 回 develop
```

**Pi 在哪？** 它在最底下那层，是执行器。**它重要，但不是主角。** 这句还是 GPT 说的。

它是 Python 写的，我是个 Java 后端。Star 数 2。

## 五、我想修正一下去年那篇文章

去年我写"我们要保持主体性"，站在岸上说要小心。

现在我在水里一年多了，想法变了。

**第一，保持主体性这个说法有点太防守了。**

你不用 AI 吗？你的竞争对手在用吗？你不用那你凭什么跟上？

"保持主体性"听着正确，但实际操作起来就是"少用"或者"小心用"，这在一个所有人都用的大环境下，等于自愿出局。

**第二，真正的"主体性"不在于不用，而在于你能不能定义规则。**
这两年出的各种 Agent 规范、上下文工程的说法，我基本都在看，也基本都在用。但它们解决的是通用问题。

真正让我能落地的，是把**我自己组的约定**写成了文件。

这两件事的区别在于——通用规范是别人的智慧，我团队的约定是我自己的判断。

**AI 不知道我们组的规矩。这不是它笨，是没人告诉过它。**

所以这套系统对我最大的意义，不是那 33 个模块，也不是省下来的那些 token。

是逼着我第一次把"我们组的规矩是什么"这件事，从脑子里搬到了纸上。

**第三，也是我去年没想到的：你不下水，永远学不会游泳。**

去年我说"过度依赖会丧失主动探索的欲望"。

现在我承认——我是被 TL 逼下水的。是工具链拉满了还不行，是被逼着去思考到底差在哪儿，才想明白的。

**如果没有人逼我，这套东西大概不会存在。**

这点挺反直觉的，但很真实。

* * *

## 六、一个搞技术的怎么说点哲学

有读者可能会觉得，这篇跟去年那篇不太一样。

是的，我刻意改了。

去年那些哲学家我堆得太满了。这次写到"打不过就加入"这个标题，我自己都有点心虚——听起来像投降，像在认输。

但想明白之后我觉得，**认输恰恰是件正经事。**

《认知保卫战》这个系列我打算继续写下去，第二篇已经写了一半了，讲的是今年 9 月 24 号那次事故——AI 把我 200 份日志删了，因为一个引号写错。

那篇我会把去年不敢写的东西写出来：**认知卸载不是你以为的那种温水煮青蛙，它有时候是一声巨响。**

* * *
