去年 2 月，我在这个号上写过一篇《AI 时代的认知保卫战：如何在算法支配下保持主体性》。

那篇文章里我说，过度依赖 AI 会让我们变得懒惰，丧失主动学习和探索的热情；说我们的成长会从主动探索变成被动接受；说我们终将成为 AI 的附庸，成为"只会使用 AI 的工程师"。

写完之后，很多朋友在后台问我：然后呢？你打算怎么办？

说实话，**当时我给不出答案。**

我只有警惕，没有方法。警惕一个人人都同意的观点，是一件很廉价的事——它显得深刻，却不解决任何问题。

大半年之后，我给自己写了一份答案。

它有 33 个模块、20 条工作流、19 份治理文档、9 份架构决策记录，637 次提交。

**它是 Python 的，而我是 Java 后端出身。**

**它已经开源了。Star 数是 2。**

* * *

## 一、九月24 号那天，AI 把我的日志删了

2026 年 9 月 24 日，我在执行一次提交。

提交信息里，我用反引号包了一个示例：\`git clean -fdx\`。

我用的是 `git commit -m "..."`，双引号。

**双引号里的反引号，是 shell 的命令替换语法。**

于是 bash 把它当成了命令，真的去执行了。

`git clean -fdx` —— `-f` 免询问，`-d` 连目录一起删，`-x` 连被 gitignore 的文件一起删。

工作树里所有未跟踪和被忽略的路径，一瞬间全没了。

**约 200 份运行日志，指标快照，本地环境配置——不可恢复。**

版本化的文件没事，100 多次提交都在 git 里。但那些日志，按我当初的设计，本来就是"机器本地、不入库"。

后来我在事故报告里写下了这句话：

> **一句话根因：运行时态与关键资产被放在"可被一条命令清除"的位置，
> 且破坏性操作无声明、无检测、无纪律。**

事故报告的作者栏，我写的是 **"AI Maintainer（事故责任方：本会话）"**。

不是甩锅给 AI。是**我**在用 AI，**我**设计的系统允许了这件事发生。

* * *

## 二、人写错和 AI 写错，不是一回事

如果是我自己手敲错了命令，那这是我的失误，我认。

但这次不一样。**这次是 AI 生成了一条命令，而它把命令跑通了。**

我人写错一个字，代价是一句话。

AI 写错一个字，它**真的去执行了**，而且执行得又快又彻底。

这才是最让我后脊发凉的地方——**AI 的错误不是"看起来像错的"，而是"看起来完全正确"。**

它没有报错，它没有犹豫，它没有反问一句"你确定要删吗"。

它直接干了。

我去年写《认知保卫战》的时候，说的是"过度依赖会让我们丧失主动学习"。

现在我要修正一下这个说法——

**依赖 AI 的最大风险，不是我们变笨了。是 AI 犯错的时候，我们看不出来。**

去年那篇文章里我也写过一句："AI 生成的方案往往缺乏技术选型的论证过程——这正是工程师最珍贵的决策能力。"

现在我知道，那句话的后半段才是重点：**决策能力的一部分，是"出错的代价由谁承担"。**

那次事故里，200 份日志没了。**它对 AI 来说毫无成本，对我来说是两周的排查记录。**

* * *

## 三、所以我做了什么：把红线画在纸上

出完这次事故，我做的事很笨——

**我开始给 AI 立规矩。**

不是那种"请注意代码质量"的口头嘱咐，是能卡住它的物理规则。

比如：

**"破坏性命令默认拒绝。"**

`git clean -fdx`、`git reset --hard`、`rm -rf`——这些全部默认拒绝执行。确需执行，必须先 `--dry-run` 列出清单，然后请求我确认。

这条规矩就是那次事故的直接产物。

还有：

**"提交信息禁用 `-m` + 反引号，一律用 heredoc 引号定界。"**

这条是 `git commit -F -` 加上 `<<'MSGEOF'`。它存在的原因只有一个：那次事故。

再比如：

**"Skill 单文件不得超过 1000 行。"**

这个是老毛病了。我有个 skill 写到 1400 行，然后 AI 开始复读——它在回答里重复文件里已经写过的段落，一遍，两遍。文件太长，它抓不住重点，就开始"回忆"。

**"每个 Skill 必须有合法的 YAML frontmatter。"**

这条我最后加的。因为缺了 description 的 skill，AI 完全不知道它该在什么时候被调用。它就在那儿躺着，安静得像个不存在的部门。

**description 不是描述，是契约。** 这是你告诉 AI 什么时候该用它。没有这条契约，它选择了不用。

现在这个系统里有 19 份这样的文档。

**它们不是设计出来的。**

**它们是一次一次被 AI 坑出来的。**

* * *

## 四、一个 Java 后端为什么会做出这种东西

可能有朋友会好奇，一个写 Java 的，怎么搞了个 Python 的东西。

其实挺顺的。

Java 后端的日常就是 Maven。多模块、`-pl` 选范围、`mvnw` wrapper、Surefire 的失败模式——这些东西我在过去十年里踩过无数次坑。

第一次让 AI 帮我跑 Maven，我就发现了问题：

`bugfix` 这个 skill 里的 `mvn -pl ... test`，散在 **3 个文件**里；
`implement` 的 validation.md 里有一份 `mvn -pl ... compile`；
`mock-test` 的 diagnosis.md 里又有一份 `mvn test -Dtest=...`。

**三套并存的写法，范围选择不一致，wrapper 处理不一致，失败诊断也不一致。**

我把这个写进了一份叫 ADR-0003 的架构决策记录里，标题就叫"java-maven as Foundation Skill"。

里面有一栏叫 Consequences，分正反两面：

**正面**——范围选择统一了、wrapper 只在一个地方检测、失败诊断只在一个地方解析、缓存友好。

**负面**——所有 skill 都必须等 java-maven 执行完；java-maven 可能成为瓶颈。

**我敢把代价写进去，是因为这确实是我自己做的选择。**

技术号最不缺的是"这个方案很好"，最缺的是"这个方案让我付出了什么"。

## 五层，和七步

这个系统最后长成这样：

| 层 | 职责 | 一句话 |
|---|---|---|
| **Workflows** | 决定做什么 | 只编排，不实现 |
| **Runtimes** | 执行怎么做 | 模板化，不即兴 |
| **Governance** | 约束行为 | 19 份规矩，违反即卡 |
| **Standards** | 定义质量 | BLOCKER / ERROR 分级 |
| **Skills** | 提供方法 | 33 个，沉淀决策逻辑 |

主链是七步：

```
prepare → spec → dev-setup → develop → review → verify → release
bugfix 是并行分支
review 打回    → 回 develop
verify FAIL    → 回 develop
```

**注意那两个"回 develop"。**

这是我最看重的地方：**AI 生成的代码不是终点，是草案。**

它必须走完 review 和 verify，任何一关不过，就被打回重做。

我算过一笔账：改完之后，一个需求从开始到进 release，平均要走 3.4 轮往返。

**是慢的。** 比我闷头写要慢。

但它慢在**不确定性**上，不是慢在打字上。

## 六、写它的时候，我也在用 AI

这件事说出来有点自相矛盾，但这是真的。

那 13 个 CLI 命令的骨架，是 AI 帮我生成的。快、省力、可运行。这部分我不打算假装是自己手搓的。

但有一件事它反复搞错。

**menu.yaml 的边界该怎么切，i18n 的文案该怎么拆——它错了四五次，每次错法都不一样。**

后来我想明白了为什么：

**因为那是我们组的约定，不是通用知识。**

AI 知道"多语言项目应该做国际化"。但它不知道"在这套系统里，结构和文案为什么必须分成两个目录"——因为这个决定是我们踩过坑之后才定下来的。

于是我必须先把规则写清楚，才能让它正确执行。

**而"把规则写清楚"这个过程本身，就是这 19 份文档的由来。**

从 7 月 31 日第一次提交，到今天，74 天，637 次提交。

其中 172 次是文档，128 次是功能，104 次是修复。

**文档比功能还多。**

这不是一个软件项目的正常比例。**这是一个人被迫把自己的判断力，一条一条写下来的证据。**

所以这一年真正的收获，不是这个系统。

**是我终于知道了自己团队的约定是什么。**

去年我写"我们要防止变成只会用 AI 的工程师"，那时候是一句没有落点的口号。

现在它有落点了：**你先得知道自己在守什么，才谈得上守。**

## 七、那张架构图

去年那篇文章末尾我写过这么一段：

> 最近在重构一个AI 辅助开发的系统时，我刻意在架构图中标注了两种路径：
> 蓝色箭头代表 AI 建议的方案，红色手绘线代表人类决策轨迹。

当时那只是一个比喻。

今年，它变成了机制。

**蓝色箭头画得极快。** 画一条 AI 建议的路径，两分钟，线条流畅，走向漂亮，每一段都合理。

**红色手绘线画得很慢。** 画一条人的决策路径要停下来想：这个能不能动？会影响到谁？违反了我们组哪条约定？想清楚了才落笔。

很多个下午，我画着画着会笑出来。

因为我发现，**这不就是去年担心的那件事吗——只不过它不在别人身上，它在我手上。**

这里有一个我必须诚实面对的悖论：

**我造这个系统，是为了防止自己变得依赖；**
**但造这个系统的过程，恰恰是我把更多判断交出去的过程。**

我没解开这个悖论，我只是让它变得可见了。

**能看见的代价，比看不见的代价，好一点。**

* * *

## 八、最后

回到《浮士德》。去年我在文末改了那句台词：

> "停一停吧，你这美妙的算法！我愿用百行低效代码，换取一次真实的认知战栗。"

今年我想给它下半句。

因为这一年我想明白了一件事——**"停一停"不是为了反对什么。**

它的对立面不是 AI，是**"不用动脑"**。

"停一停"是为了画那条红线。它笨、慢、不好看。但它是你的。

这次事故也让我改了一个想法。我原本以为给 AI 立规矩是为了"控制"它，写完才发现不是。

**规矩的真实作用，是让我自己变得可控。**

这个系统现在 Star 数是 2，Fork 是 0。我知道它离"好用"还很远，目前主要是我自己在用，规模化的验证还没做过。

我不太打算拿它去讲什么方法论，也不劝你装。

但如果你也在用 AI 写代码，如果你也有过"跑通了、可我就是不敢 merge"的那 20 秒——

**欢迎来看看，顺便翻翻那份事故报告。**

GitHub：`github.com/Syske/ai-system`

回复【**aic**】，我把 19 份治理文档清单、7 步工作流的契约文件，以及那份 INCIDENT 报告，都发给你。

* * *

如果你身边也有人正在用 AI 赶进度——**转给他。**

让他知道，有一种用法，是慢一点，但站得住的。
